# hcache-uring 复赛延迟复盘与改进方案

本文根据保留下来的代码、参赛者提供的复赛题面及第四名成绩截图，分析高吞吐与较高请求延迟同时出现的原因，并给出可以逐步实施的改进方案。

优先方向是保留内存分片和每核处理的优势，移走事件循环中的同步持久化，约束排队和调度时间，再减少跨核往返。历史评测日志、运行环境及逐接口结果已经缺失，因此下文提出的是有代码依据的假设和验证计划，不能认定某项机制就是当年的唯一根因，也不承诺具体性能提升。

分析基线为提交 `4380f4921ce6cfeb5efa869d142d9160adb60e7d`，主要对象是 CMake 实际构建的 `src/hcache.cc`，不混用 `hcache-dpdk.cc` 的行为。无法确认该提交与截图对应的参赛镜像完全一致。本次交付只增加文档，没有实施以下代码改动，也没有运行性能实验。

## 成绩说明了什么

参赛者确认截图属于复赛，第四名为本队。以下保留的是截图中的得分，不是原始 QPS 或毫秒数。

| 项目 | 本队 | 总分第一名 | 本队减第一名 |
| --- | ---: | ---: | ---: |
| init_score | 0.00 | 0.00 | 0.00 |
| api_score | 3690.00 | 3810.00 | −120.00 |
| qps_score | 18188.89 | 18152.55 | +36.34 |
| delay_score | 1584.21 | 2508.33 | −924.12 |
| 总分 | 23463.10 | 24470.88 | −1007.78 |

延迟项占双方总分差距的约 91.7%。本队吞吐得分已经略高于总分第一名，优先投入延迟优化有成绩依据；正确性仍有 120 分差距，延迟优化需要同时守住数据语义。

题面给出的公式为：

```text
score = 10/T + 10n + 50 × (qps/10000) × k + 50 × (1/time_delay) × m
```

其中 T 为加载时间，n 为正确性评测中取得相应分数的接口数量，k、m 分别为吞吐和延迟评测接口数量。由于缺少评测器的实际汇总实现、接口权重和延迟单位，不能把得分还原为确定的 QPS、平均毫秒数或 P99。

仅在双方 m 相同，且延迟项确实按一个 time_delay 计算时，`2508.33 / 1584.21 ≈ 1.583` 才意味着本队计分延迟约为对方的 1.58 倍；若实际逐接口计算倒数再求和，则不能这样反推整体平均延迟。

作为分值敏感性参考，若其他项不变、仅将延迟得分提高到第一名水平，总分会是 24387.22，仍差 83.66。这只是算术对照，不是优化后的成绩预测。README 中的历史表述“QPS 第一”没有对应评测批次记录，本文的定量判断以这张复赛截图为准。

## 赛题约束与原设计的取舍

用户提供的题面说明：初赛单机，复赛改为多机；每台评测 ECS 为 4 核 16 GB，规格 ecs.g7.xlarge；请求使用 HTTP，压测由多个 API 组合构成，场景可能变化。启动时必须加载规定的全部 LevelDB 格式磁盘数据，单机磁盘数据可能超过本机内存；评测会发生宕机重启，允许丢失数据，但错误操作不得分。

这些约束解释了原方案的选择：

- 按机器分片可以利用集群总内存，避免每台机器保存全部数据。继续优化时也不能默认全量复制一定放得下。
- 按核心分片使普通查询在所属核访问内存表，减少共享锁竞争。连接与数据所属核不同，则要支付跨核排队成本。
- 协程、忙轮询、连接复用和批量发送使多个请求的 I/O 等待重叠，降低单位请求的调度和提交开销。
- 持久化可以保护重启后的正确性，但会消耗 CPU、内存和磁盘带宽；4 核环境里，增加后台线程也不是免费资源。

吞吐衡量一段时间内完成了多少请求，延迟衡量一个请求从开始到完成经历多久。对同一稳定负载，Little 定律给出 `平均在途请求数 = 吞吐率 × 平均延迟`：可以通过更多在途请求维持高吞吐，但它们各自仍在等待。固定并发、相同工作负载下，二者也受到这个关系约束，不能认为毫无关联。本赛题还有多个接口与独立计分项，聚合吞吐得分更不能代替逐接口延迟。

## 代码中可以确认的延迟来源

| 代码事实 | 可能产生的代价 | 证据 |
| --- | --- | --- |
| key 分别哈希到机器和核心，HTTP 与 RPC 连接轮询分核 | 远程请求增加一次 RPC 往返，目标机器还可能跨核往返 | [get_shard 和 xcore_query](../src/hcache.cc#L186)、[handle_http](../src/hcache.cc#L1300) |
| exceed_quota 恒返回 false | batch、list、zrange 中的主动让出不生效，大请求可长时间占用事件循环 | [exceed_quota](../src/hcache.cc#L80)、[批量操作](../src/hcache.cc#L343) |
| run_pending 清空一个来源队列后才处理下一个，任务上限被注释 | 繁忙来源拖延其他来源和下一轮网络处理 | [run_pending](../include/threading.h#L107) |
| 每核定时调用两个 DB 的 Flush，未修改默认 wait 选项 | 存在待刷数据时，同步等待可能阻塞该核的网络与任务调度 | [db_flusher](../src/hcache.cc#L1818) |
| delay_add_persist 等函数直接 Put/Delete，batch 直接 Write | 写入变慢或发生 write stall 时，事件循环一起停顿 | [单条写](../src/hcache.cc#L218)、[批量写](../src/hcache.cc#L343) |
| RPC 发送后立即归还连接，服务端每条连接逐请求执行 | 同连接积累未完成请求，大请求挡住后面的小请求 | [send_rpc_request](../src/hcache.cc#L902)、[handle_rpc](../src/hcache.cc#L648) |
| list 分发到多个节点及核心，收齐结果才响应，空分片也会创建任务 | 完成时间受最慢分片影响，并有不必要的空任务调度 | [xcore_list](../src/hcache.cc#L413)、[HTTP list](../src/hcache.cc#L1552) |
| 写接口先发成功，再解析或修改数据 | 当前响应时间与实际完成时间分离，工作可能拖延后续请求 | [HTTP add 和 batch](../src/hcache.cc#L1488) |
| 跨核队列容量为 256，push 未检查成功与否 | 满队列时可能丢失已挂起协程，表现为请求悬挂或超时 | [io_queue](../include/threading.h#L20) |

前三类调度与转发机制可以在纯内存查询中产生额外等待。同步持久化的影响取决于是否有脏数据、磁盘状态和后台工作量，不能把所有纯读延迟归因于 Flush。500 ms 是定时器间隔，不是每条请求固定增加的延迟。

库行为也需要按版本理解：锁定版本的 [RocksDB FlushOptions](https://github.com/facebook/rocksdb/blob/849cf1bf68673ae114638276194e12cca583c6c6/include/rocksdb/options.h#L1798) 默认 `wait=true`；[uringpp 的 poll_no_wait](https://github.com/howardlau1999/uringpp/blob/b4de8213834aac2fb56c7587da27112c7a02ea75/include/uringpp/event_loop.h) 先提交 I/O，再处理完成事件。回调中生成的新 I/O 通常等下一轮提交，期间的长任务会推迟发送；队列满时库也可能提前提交，并非要等攒满才发送。

[uringpp task](https://github.com/howardlau1999/uringpp/blob/b4de8213834aac2fb56c7587da27112c7a02ea75/include/uringpp/task.h) 创建后立即运行，因此批量分发中的逐个 co_await 是收集并发任务结果，不能误判为串行发起 RPC。HTTP 每 1000 项、RPC list 每 256 项发送，是同一个请求内的批量，也不是凑齐多个独立请求才响应。

## 建议的实施顺序

| 顺序 | 改动 | 希望解决的问题 | 主要验收证据 |
| --- | --- | --- | --- |
| P0 | 建立新基线，明确成功响应语义，修复满队列丢任务 | 统计口径失真、永久等待、错误执行 | 成功数、失败数、未完成数闭合；正确性基线可复现 |
| P1 | 将 Put/Delete/Write/Flush 移到有界、有序的持久化执行侧 | 网络事件循环被磁盘等待阻塞 | 写压力下事件循环停顿及读延迟下降，恢复顺序正确 |
| P1 | 给来源队列与完成事件处理设置预算并轮转 | 热队列拖住其他队列和 I/O 提交 | 混合负载下各来源等待时间受控 |
| P1 | 批量分发跳过空节点和空核心分片 | 不必要的 RPC、任务切换及空批次写入 | 相同返回结果下，内部请求数与任务数减少 |
| P2 | 安全地切片大请求，并限制 RPC 未完成请求 | 大请求独占与连接队头阻塞 | 小请求延迟改善，大请求仍能完成，无内存积压 |
| P3 | 将 RPC 连接定向到数据所属核 | 不必要的跨核往返 | 同类远程查询的跨核次数及延迟下降 |
| P4 | 调整批量大小、提交策略、CPU 分配与复制开销 | 剩余 CPU 和 I/O 开销 | 在一致语义与负载下得到更好的吞吐延迟曲线 |

第一轮集中完成 P0 和 P1。修改按单项保留开关或独立提交，先分别测量，再测试组合；避免一次更换网络栈、数据库和调度器而无法解释收益来源。

## 持久化应怎样移出事件循环

建议先建立每个数据分片的有序持久化通道，再用少量执行线程服务这些通道。逻辑上每个分片的写入按顺序执行，不要求机械地为每核再创建一个忙轮询线程。比较不同线程数量及 CPU 分配时，必须把 RocksDB 后台线程的竞争也算进去。

拟议的数据流为：

```text
输入校验 → 到达数据所属核 → 预留持久化队列容量
        → 按顺序修改内存并发布拥有自身数据的写任务
        → 持久化执行侧合并写入及管理 Flush
        → 将完成或失败通知可靠地送回所属事件循环
```

队列中的 key、value 和 WriteBatch 必须拥有自己的存储，不能借用会复用的请求缓冲区或 string_view。执行线程显式持有 DB 指针及分片标识，不能依赖原事件循环的 thread_local 数据。需要检查 RocksDB Status，记录失败，并在正常关闭时停止接纳新写、排空已接纳任务、完成约定的同步后再关闭 DB。

内存修改顺序必须与持久化顺序一致。特别是 batch 开始分段让出后，不能保留“先修改全部内存，最后才提交 WriteBatch”的做法。例如 batch 已写入 k 后让出，另一个请求删除 k 并先入持久化队列，随后 batch 才提交 Put(k)，重启后就可能让已删除的 k 重新出现。应按块预留容量、执行内存修改并发布对应写入；若 API 要求批量原子性，则需另行设计，不能静默把原子批量改成分块可见。

`Flush(wait=false)` 可以作为单独实验，观察去掉等待完成后的变化，但它仍是一次同步 API 调用，不保证调用时间恒定，也不能消除写入阻塞或后台 compaction 竞争。更完整的方案是把 Flush 控制一起移到执行侧，跟踪尚未完成的 Flush，避免盲目按时间叠加提交。RocksDB 在 flush 或 compaction 跟不上时可能阻塞应用写线程，应同时记录其 LOG 和 stall 指标。[RocksDB Write Stalls](https://github.com/facebook/rocksdb/wiki/Write-Stalls)

响应时机需要明确区分：

| 成功响应承诺 | 何时响应 | 验证重点 |
| --- | --- | --- |
| 内存可见 | owner 已完成内存修改，持久化任务已可靠接纳 | ACK 后从其他连接及节点读取可见；崩溃仍可能丢失 |
| 进程崩溃恢复 | 等待达到选定 WAL 策略所承诺的状态 | 强制结束进程再启动后的已确认记录恢复 |
| 系统崩溃或掉电恢复 | 等待规定的持久化同步完成 | 需要相应故障模型验证；仅杀进程不足以证明 |

远程写也应等待 owner 达到相同承诺再回复。当前代码的提前成功响应应作为历史基线单独保存；修正响应语义后，当前写接口测得的延迟可能上升，这是完成定义改变，不能混成一组性能对比。

赛题允许丢数据扣分，因此可以比较不同持久化策略的延迟和恢复损失，但必须报告损失数量与完成边界。关闭 WAL 的损失窗口不能写成“最多 500 ms”：它还包含队列积压、调度、Flush 耗时和失败。当前代码也不是全部操作都关闭 WAL：单条 add/del 使用新建 WriteOptions，部分其他操作使用由 INIT_DIRS 分支修改的全局选项。[写入选项](../src/hcache.cc#L218)、[加载分支](../src/hcache.cc#L1899)

## 调度与大请求应怎样改

先限制每轮处理的任务数量或时间，轮换来源队列的扫描起点，交替处理跨核任务、网络完成事件和 I/O 提交。可以把 32/64 个任务和 50/100/250 微秒作为待测参数组合，而非生产默认值或已验证目标。一个任务自身不返回时，调度预算无法抢占它，因此移除同步阻塞和切片长任务仍是必要工作。

同核主动让出应进入下一轮就绪队列。当前“重新放回正在清空的队列”的方式可能立即又执行自己，即使恢复 exceed_quota，也不一定给其他队列或网络轮询机会。

不能直接将 exceed_quota 改回计时判断就结束：

- zrange 跨潜在挂起点持有 zset 的引用和迭代器。其他请求删除整个 zset 会销毁对象；更新集合也可能使迭代状态失效。需先设计对象生命周期、稳定游标或版本化快照，并明确并发查询语义。
- 同一 score 下大量 value 的内层循环也要切片，否则仍有长时间不可让出的区间。批量解析、结果复制和 JSON 序列化同样需要观察耗时。
- list 按项重新查找并复制 value，比较容易分段，但分段后可能读到不同时间点的数据，不能宣称它提供一致快照。
- batch 切片必须与前述内存及持久化顺序一起修改。

先按确定的 API 语义实现，再做性能比较。若完整历史 API Spec 无法恢复，就记录新基准采用的语义及差异，不把弱化语义产生的提速视为等价优化。

## 队列和 RPC 应怎样控制等待

跨核投递失败时，源事件循环要保留任务，并在后续轮次有限重试；同时设置有界待投递区及入口接纳额度。返回结果和取消通知也要有可靠的回程容量，避免所有额度都被新请求占满，导致已执行任务无法完成。

同一源到目标通道存在待投递任务时，新任务也须按序排入待投递区，不能抢先进入腾出空间的队列；或者通过序号在 owner 侧有序接纳。重试和取消不得破坏已承诺的操作顺序，否则旧写入可能越过后来的删除，重新产生错误数据。

不能在满队列时自旋等待空间，双向投递可能互相阻塞；也不能简单让 await_suspend 返回 false 后在原核继续，因为随后访问的是目标核的 thread_local 状态。目标是每个已接纳请求都有且只有一个完成或失败结果。超过容量时应停止继续读入、等待额度或明确失败，并把失败计入统计，不能丢任务或无限加大队列。

RPC 池需要记录每条连接的未完成请求数和字节数，在完成后释放额度，并同时限制每个 peer 与全局总量。可比较“小查询与大请求分池”和“有限流水线深度”，但分池不能破坏同 key 必需的操作顺序，也不能只让小请求快而使大请求饥饿。

不建议直接把同连接的每条请求都 detach 并发执行：必须先解决输入缓冲区所有权、写操作顺序和响应帧的串行发送。当前 req_id 实际编码 pending_call 指针；加入超时前，应改为稳定请求 ID 和所属事件循环管理的 pending 表，使完成、超时、取消只有一个终态，迟到回复可安全丢弃。超时不能直接释放仍可能被回复引用的对象，也不应无条件重试未确认结果的写操作。[请求生命周期](../src/hcache.cc#L912)、[回复分派](../src/hcache.cc#L1253)

减少跨核往返放在上述工作之后：内部 RPC 通过握手或明确的 worker 端口将连接一次性分配到目标数据核，连接池按 peer、目标核和源事件循环索引，按需创建并限制总数。协议需协商目标节点的核心数和分片版本，不能依赖 accept 顺序或单独使用 SO_REUSEPORT 来保证路由。

批量请求先按节点和核心分组，跳过空分片。单 key 请求可因此减少目标机器的跨核往返；客户端仍可访问任意节点，跨机开销不会自动消失。全量复制、DPDK、SQPOLL 或重写存储引擎暂不列为第一轮工作，它们涉及额外内存、CPU 或维护成本，应由后续测量决定。

## 没有历史环境时如何验证

新实验的目标是比较当前代码与改进版本，不是复现比赛分数。尽量使用三台独立的 4 核 16 GB 服务端和独立压测端；若硬件不同，记录 CPU、内核、磁盘、网络、绑核及资源限额。单机容器可以验证逻辑和调度，但不能代表三机网络性能。

固定基线提交、子模块版本、编译选项、随机种子和数据集。先确认全部数据加载完成，再开始计时。数据应覆盖普通 KV 和有序集合，分别记录 key/value 大小、批量项数、范围结果大小、命中率与热点分布；这些都是新实验参数，不冒充官方数据分布。

| 场景 | 对照方式 | 要回答的问题 |
| --- | --- | --- |
| 小 query | 低并发下分别测同核、跨核、跨机 | 固定转发成本有多大 |
| 小请求混合大 batch/list/zrange | 固定小请求到达率，逐渐增加大请求规模与比例 | 调度和连接队头阻塞是否拖慢小请求 |
| 读写混合及慢盘 | 逐步增加写比例，比较持久化改动前后 | 事件循环停顿是否与写入或 Flush 相关 |
| 热 key 与满队列 | 定向压向同一 owner，并制造双向队列拥塞 | 背压是否生效，是否丢失或重复恢复任务 |
| 持续写入与故障恢复 | 随机时刻结束进程并重启，对照已确认操作序列 | 响应承诺、持久化顺序与实际损失是否一致 |

定向正确性测试至少包括：ACK 后跨连接读取、同 key 写入删除再写入、batch 分段时穿插删除、zrange 与删除更新交错、队列满、持久化失败、RPC 断连和迟到回复。对时序测试记录每个 key 的确认及持久化序号，检测重启后旧值覆盖新值或删除失效。

性能测试同时使用固定并发和固定到达率。前者观察饱和吞吐，后者观察相同输入负载下的排队与延迟。记录计划发送时间、实际发送时间和最终响应时间；服务端变慢时，客户端如果随之少发请求，会掩盖原本应当经历的等待，这类遗漏需在压测模型或统计中处理。[HdrHistogram 对 coordinated omission 的说明](https://github.com/HdrHistogram/HdrHistogram)

每组实验报告：

- 输入请求速率、成功吞吐、错误、超时，以及停止发流并排空后的未完成请求数；不能只统计成功请求的延迟。
- 每个 API 的平均值、P50、P95、P99、P99.9 和样本数，以及首字节与完整响应耗时；样本不足的分位数明确标记。
- 各核队列等待、执行时间、事件循环最大停顿、准备响应到实际提交 I/O 的等待、RPC 未完成数量及字节数。
- 持久化队列条数及字节数、最老任务年龄、Flush 耗时、write stall、CPU、RSS、磁盘及网络吞吐。

阶段打点使用各进程本地单调时钟，以请求 ID 关联；未经时钟同步校正，不直接相减不同机器的时间戳。先测量打点本身的成本，再决定采样比例。

预热后测试需覆盖多个 Flush 周期及持续写入后的后台工作，检查队列是否达到稳态。每个改动做多次交替 A/B，对相同数据集、完成语义和输入速率比较，同时报告各版本自己的饱和点；不要只取最快一次，也不要把持续增长的积压当成可持续吞吐。

## 改动保留的判断标准

判断一次改动是否有效，应先确认成功语义和错误率没有被隐藏改变，再看同输入负载下的延迟分布是否改善，最后检查持续吞吐、资源消耗和崩溃恢复损失。允许用一部分峰值吞吐换取更低延迟，但代价应显式记录，而不是只展示其中一个指标。

建议为每轮实验保存以下记录：

| 版本与单项改动 | 完成语义 | 负载与资源配置 | 成功吞吐及错误率 | 各接口平均延迟与 P99 | 队列及恢复损失 | 是否保留 |
| --- | --- | --- | --- | --- | --- | --- |
| 基线及后续实验 | 待记录 | 待记录 | 待测 | 待测 | 待测 | 待决定 |

比赛的确切权重和评测场景已无法重建，因此不设“必然追回多少分”的目标。可交付的改进应是可解释、可重复的测量结果：知道请求在哪里等待，缩短等待后没有引入错误，并能说明吞吐与持久化付出了什么代价。
